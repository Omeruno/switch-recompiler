# Итоги проекта switch-recompiler

## Что было целью
Запускать программы Windows XP прямо на Nintendo Switch (homebrew, libnx),
без Linux и без чужих эмуляторов, всё своё: загрузчик PE, процессор x86,
Win32 и MFC. Первые цели: Сапёр (`winmine.exe`) и Paint (`paint.exe`).

## Что получилось

**Сапёр работает полностью, на реальном железе.** Геймплей, меню, диалоги,
звук из ресурсов `WAVE`, сохранение настроек в виртуальном реестре,
управление тачем и стиком.

**Paint работает частично.** Это настоящее MFC-приложение (MFC42u), и оно
оказалось на порядок сложнее Сапёра:
- работают окно, меню, тулбар (настоящие иконки из ресурса), палитра
  (настоящие 28 цветов из кода paint.exe);
- рисование пальцем и стиком;
- инструменты: Карандаш, Кисть, Ластик, Прямоугольник, Эллипс, Пипетка;
- падают Линия, Текст, Лупа;
- ничего не рисуют Заливка, Распылитель, Кривая, Многоугольник,
  Скруглённый прямоугольник и выделения.

**Инфраструктура**, которая пригодится в любом похожем проекте:
- декодер и интерпретатор целочисленного x86;
- программный GDI;
- очередь сообщений с честными `PeekMessage(PM_NOREMOVE)` и вложенными
  вызовами WndProc;
- разбор ресурсов (меню, диалоги, RLE4-битмапы, WAVE);
- генератор таблицы ABI для MFC42u по ординалам (`tools/mfc_abi.py`);
- 5 регрессионных тестов и CI.

## Почему проект закрыт

### 1. Ручная эмуляция MFC — тупик по трудозатратам
Почти все баги Paint (подробно в `docs/archive/`) имели одну природу:
наши заглушки MFC не строят настоящее внутреннее состояние библиотеки.
Примеры:
- `CDC::FromHandle` не был реализован, и код разыменовывал мусор;
- синтезированные `CDC` имели `vtable = 0`, и падал любой виртуальный
  вызов;
- ординал 5784 (`CDC::SelectObject(CPen*)`) попадал в общую заглушку,
  которая снимала со стека не столько байт, сколько нужно. Стек вызывающей
  функции сдвигался, и краш случался в совсем другом месте;
- `CWinThread::Run` годами выбрасывал сообщения из очереди, потому что был
  написан до появления диспетчеризации.

Каждая починка вела к следующему крашу глубже по цепочке. Для Пипетки
пришлось обойти цепочку и реализовать инструмент прямо на хосте. Так
можно довести Paint до конца, но каждый новый инструмент и каждое новое
MFC-приложение требуют того же объёма работы заново.

### 2. Цель «игры эпохи XP» этой архитектуре недостижима
Для игр (например, Mirror's Edge, Unreal Engine 3) нужны:
- x87/SSE (сейчас их нет совсем);
- потоки, загрузка DLL, исключения;
- Direct3D 9 поверх GPU Switch, DirectSound, DirectInput;
- скорость: интерпретатор без JIT в десятки раз медленнее, чем нужно.

Это годы работы для команды.

### 3. Это уже сделано
Autorun (раньше Wine-NX, <https://github.com/autorunhq/autorun>) — порт
Wine под Horizon OS. В нём уже есть:
- Box64 (ARM64-динарек) для 32-битного x86;
- DXVK для Direct3D 9–11 и Mesa для GPU Switch;
- тач, контроллер, сенсорная клавиатура.

Он запускает Need for Speed Underground 2, Halo, WarCraft III, Quake III.
Для игр с фиксированным адресом загрузки (UE3 и т.п.) ему нужен патч
Mesosphere «low window», который ставит Quick setup. Для пользователя,
который хочет запускать программы и игры XP на Switch, это правильный
инструмент.

## Уроки
1. **Начинать с поиска существующих решений.** Стоило искать готовое до
   первой строки кода, а не после двух месяцев.
2. **Эмулировать нижний слой, а не верхний.** Win32 (kernel32, user32,
   gdi32) хорошо задокументирован и конечен. MFC — огромная библиотека с
   внутренним состоянием. Загружать настоящий `mfc42u.dll` и исполнять его
   интерпретатором честнее и в итоге быстрее, чем подделывать его ординал
   за ординалом. По той же логике Wine, Boxedwine и Autorun реализуют
   систему, а не библиотеки поверх неё.
3. **Соглашение о вызовах и размер аргументов — это всё.** Ошибка в 4 байта
   очистки стека проявляется не там, где сделана. Таблица ABI, построенная
   из декорированных имён, окупилась многократно.
4. **Никогда не гадать.** Каждая гипотеза проверялась трассировкой или
   дизассемблированием. Все «очевидные» объяснения геометрии иконок
   тулбара (28px, 20px, 14px) оказались неверны, помогло только чтение по
   пикселям.
5. **Отладка на железе — отдельная дисциплина.** Консоли нет. Лучшим
   каналом стали цветные полосы, нарисованные прямо во фреймбуфер в обход
   GDI.
6. **Старый код стареет незаметно.** Главный баг Paint жил в самой ранней
   функции (`Run`), вокруг которой выросла вся остальная система.

## Если кто-то захочет продолжить
Порядок от самого полезного к менее полезному:
1. **Загрузчик DLL**: базовые релокации, таблица экспорта, `DllMain`,
   связывание импортов DLL между собой. Тогда можно загружать настоящие
   `mfc42u.dll` и `msvcrt.dll` из своей копии XP и удалить большую часть
   `Impl_Mfc*` из `host_functions.cpp`.
2. **Добить Win32 под настоящую MFC**: функций, которые импортирует
   `mfc42u.dll`, больше, чем у paint.exe. Список даст `tools/check_imports.py`.
3. **x87 FPU**: без него не пойдёт большинство программ сложнее Сапёра.
4. Только потом остальные инструменты Paint: с настоящей MFC они,
   скорее всего, заработают сами.

Для игр продолжать этот проект не стоит: лучше помогать Autorun.
