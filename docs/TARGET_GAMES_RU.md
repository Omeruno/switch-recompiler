# Цель: PC-игры и приложения на Nintendo Switch

Пользователь зафиксировал долгосрочные ориентиры: **Spore, Mirror’s Edge,
The Sims 3 и Lineage 2 Classic (пример — Asterios)**. Это цели будущей совместимости, а не список уже работающих игр.
Сборки/версии и их PE/API/шейдерные зависимости ещё не исследованы в этом пакете;
ни запуска, ни игрового FPS для этих названий не подтверждено.

Проект строится как слой исполнения и совместимости PC-приложений поверх
Horizon/homebrew API. XP-подобная оболочка нужна для файлов, установки и запуска.
Paint и Сапёр — удобные ранние проверки общих механизмов, а не конечный предел
проекта. Оптимизации должны помогать всем приложениям поддержанного пути;
исключения по имени EXE и успешные заглушки не заменяют реализацию.

## Как использовать CPU и GPU Switch

| Гостевая задача | Целевой путь | Текущее состояние |
| --- | --- | --- |
| Исполнение x86 | Корректный перевод горячего кода x86 в ARM64, выполняемый процессором Switch; interpreter fallback | Интерпретатор есть; полноценного dynarec/code cache нет |
| Win32/CRT/потоки/файлы | Реальные host-реализации через доступные API Horizon/libnx | Значительная ограниченная база; не полная Windows/NT и не полная параллельность guest threads |
| DirectDraw/Direct3D | Перевод графических команд, ресурсов и шейдеров в поддержанный host GPU backend | DirectDraw/D3D не реализованы; существующий GPU-композитор и GPU-GDI этого не заменяют |
| Звук/ввод/хранение | Игровые API → реальные host audio/input/filesystem backends с правильным временем жизни | Файловая и вводная база есть; необходим отдельный аудит игровых API и звука |

x86-инструкции не исполняются напрямую на ARM64. DirectX также нельзя просто
передать GPU Switch без перевода API/шейдеров и согласования памяти. Нативное
исполнение переведённого ARM64-кода и аппаратное выполнение переведённых GPU
команд — желаемый путь, но его требуется реализовать и проверить.

Использовать доступные процессорные ядра и GPU нужно там, где этого требует
нагрузка. Для параллельного guest execution отдельно нужны thread safety,
модель памяти/атомики, ожидания и корректное владение USER/GDI/ресурсами;
нынешний кооперативный планировщик не доказывает такую готовность.
Бюджеты CPU/RAM/GPU зависят от режима запуска, Horizon и системных резервов.
Цель — полезная производительность при корректном выполнении, а не обязательная
100% загрузка каждого блока. Полную мощность и определённый FPS без замеров
на конкретной игре/консоли не обещаем. Аппаратные проверки пока отложены.

Текущий аппаратный вывод использует OpenGL/Mesa. Backend для игрового API
выбирается по реально доступным homebrew возможностям, поддержке операций,
точности и измерениям; готовность Vulkan/NVN или другого будущего backend
не предполагается. Избегать лишних readback/upload и двойной CPU/GPU работы.

## Целевые нагрузки для будущего аудита

В таблице — вопросы будущего исследования, а не утверждение об уже изученных
импортах конкретного дистрибутива. Приоритет охвата D3D9 следует проверить на
выбранных оригинальных Windows-сборках этих игр; это ещё не принятое решение
о реализации всего DirectX или о поддержке любых переизданий.

| Ориентир | Что проверить на выбранной версии |
| --- | --- |
| Spore | Архитектура EXE/DLL, графический API/шейдеры, CPU/SIMD, ресурсы и сохранения, звук, ввод |
| Mirror’s Edge | Графический API/шейдеры, загрузка уровней/текстур, потоки, физические/middleware DLL и их CPU-путь, звук, лимиты памяти |
| Lineage 2 Classic / Asterios | Зафиксировать конкретный сервер/клиент/chronicle и архитектуру EXE/DLL; проверить графический API/шейдеры, launcher/обновления, сетевые API/DNS/TLS/авторизацию, зависимости защиты клиента, потоки/таймеры, загрузку мира/ресурсов и устойчивость длительного сетевого сеанса |
| The Sims 3 | Simulation CPU time, длительные сеансы, рабочий набор памяти, streaming/сохранения, графика, потоки и состав дополнений |

Для Lineage 2 Classic / Asterios название сервера не определяет версию клиента.
Нужны точная сборка, соответствующий сервер и отдельные результаты: загрузка →
launcher/авторизация → выбор персонажа → вход в мир → ввод/звук/сеть → длительный
сеанс и корректное отключение/переподключение. Сетевой backend и совместимость
launcher/защиты — ещё не реализованные критерии; успешные заглушки их не закрывают.

Не смешивать изначальные Windows-версии, обновления, launcher-зависимости и
переиздания. Для каждой выбранной сборки зафиксировать архитектуру, зависимости
и последовательные фактические результаты: загрузка → меню → игровая сцена →
ввод/звук → сохранение/повторная загрузка → продолжительный сеанс → измерения.
PE32+ и x64 не входят в текущую x86-32 базу; расширение ISA требует отдельного плана.

## Крупные рубежи и критерии

1. **D/E/F — фундамент:** корректный loader/API/lifecycle, память, файлы,
   сохранения, ввод и диагностика. Закрывать конкретные несовместимости
   воспроизводимыми общими реализациями.
2. **Оставшийся G4b.2:** окна/DC, CPU/DIB/ROP-барьеры и основной texture bridge.
   Это нужный стык ресурсов/вывода, но не замена игрового D3D backend.
3. **G CPU:** полноценный x86→ARM64 dynarec с oracle/fallback, блоками/code cache,
   invalidation/self-modifying code, icache, fault/SEH, SSE/x87 и измерением
   HLE-переходов. Минимальный JIT-probe42 не закрывает этот рубеж.
4. **H и игровые зависимости D:** после аудита выбрать первый узкий графический
   контракт и публичные fixtures. Для этих целей приоритизировать исследование
   D3D9: shader/resource/state/draw/readback/present/reset, затем наращивать
   поддержанный охват. Не считать большой DirectDraw-переводчик обязательной
   предварительной работой без зависимостей выбранных игр. Звук/streaming,
   таймеры и middleware — реальные самостоятельные gates, а не успешные stubs.
5. **I — игры как продукт:** матрица выбранных версий, функциональная совместимость,
   память, CPU/GPU frame time, передачи/синхронизация, audio underruns,
   корректность сохранений и устойчивость длительных сеансов на Switch.

Это зависимости разных направлений, не обещание полностью завершать каждую
букву до следующей. Приоритеты G CPU / H / D уточняются по публичным тестам и
аудиту целевых игр; сначала измерения, затем оптимизация. Установщики/архивы
остаются в [своём плане](F_INSTALL_AND_ARCHIVES.md): установка не доказывает
совместимость или производительность игры.

Текущая очередь остаётся в [ACTIVE_ROADMAP.md](ACTIVE_ROADMAP.md).
